# Debug investigations

Documented bugs and open questions from working with the OpenDAW SDK. Each file describes a specific behaviour, the mechanism (verified against current SDK source), and how to reproduce it using one of the unlisted debug demo pages.

## Conventions

- **One file per investigation.** Filename in kebab-case, descriptive, no date or number prefix. Sort by topic, not chronology.
- **Each note states the SDK version it was verified against.** Code citations (file:line) are point-in-time and decay — re-verify before quoting.
- **Focus on evidence and repro, not advocacy.** Document what's observed and how to reproduce it; label what's inferred from source-tracing as inferred. The goal is to make the symptom reproducible by anyone reading the note — diagnosis, recommendations, and contract questions are out of scope.
- **Repro pages are unlisted.** They live alongside the regular demos but are not added to `src/index.tsx` or `public/sitemap.xml`. The HTML carries `<meta name="robots" content="noindex, nofollow">`. They're reachable only by direct URL and are intentionally minimal — one button, one configuration, one thing to listen for.
- **Proven browser-probe techniques** (no SDK or page changes needed): patch
  `OfflineAudioContext.prototype.startRendering` to capture rendered buffers; intercept
  `MessagePort.prototype.postMessage` to log engine transport commands; pull `project`
  from a mounted component's React fiber. All three were used to close the seam and
  mode-swap investigations.
- **All demo pages boot the WASM engine (the only engine).** Their
  offline scan always routes through `OfflineEngineRenderer` —
  `OfflineAudioContext` + `createEngine` throws with the WASM `EngineVariant` once any wasm
  engine booted on another context (`ensureReady` registers the processor only on the first
  context — see [wasm-ensure-ready-second-context.md](./wasm-ensure-ready-second-context.md)).
  The live WASM transport can take 20–30 s+ after `play()`
  before position advances on these pages; the offline scan does not depend on it.
  **Update 2026-07-16:** observed at SDK 0.0.159; re-tested at 0.0.160 and the delay did
  NOT reproduce — position advanced in ~3.3 s.
- **Claims about runtime behaviour must be empirically verified, not inferred.** Tracing through SDK source produces plausible-looking explanations but can include unverified steps. If the doc states "X happens because Y," `Y` must be confirmed by logging the relevant value at runtime, stepping through with a debugger, or otherwise observing it directly. Citation of file:line for `Y` is not verification of `Y` — it's verification that the code at that location *exists*. When in doubt, present the symptom and repro without the mechanism, and let the maintainer diagnose.

## Index

- [time-pitch-start-position-pop.md](./time-pitch-start-position-pop.md) — Audible pop when starting playback inside a mid-file silent gap bracketed by audio, with `AudioTimeStretchBox` attached at `playbackRate = 1.0`. TimeStretch-specific (not in NoStretch, not on head-of-file silence). Mechanism identified: `TimeStretchSequencer.#handleTransientBoundary` starts the voice at the enclosing segment's onset rather than the playhead position, replaying pre-gap audio through the pitch-shift pipeline. Mode-swap "playhead reset" resolved — the page's own defensive `setPosition` call was the confounder. SDK 0.0.165 adds a fade-in on mid-source voice starts that is expected to mask this pop — re-verify pending (see the note's 2026-08-05 addendum). Repro: [`time-pitch-start-position-debug-demo.html`](../time-pitch-start-position-debug-demo.html).
- [splice-click-cross-file.md](./splice-click-cross-file.md) — Audible click at exact region boundaries when consecutive same-track regions reference different audio files. **Resolved at SDK 0.0.165: automatic SDK handling.** The engine rings every region out past its end via a read-past-the-end release tail and fades in whenever a region starts partway into its source (the fade-in guard consults `loop_offset`), so a cross-file splice gets a genuine ~20 ms crossfade. Repro page is now a regression check. Repro: [`comp-lanes-debug-demo.html`](../comp-lanes-debug-demo.html).
- [fade-out-end-of-file-pop.md](./fade-out-end-of-file-pop.md) — Audible click at the end of a clip whose fade-out ends exactly at the audio file's end. Fixed upstream in core 0.0.145 (keep-guard added to `#updateOrCreatePitchVoice`); re-verified clean at SDK 0.0.154 / core 0.0.152. Page is now a regression check for this fix. Repro: [`fade-out-end-of-file-debug-demo.html`](../fade-out-end-of-file-debug-demo.html).
- [shared-source-double-process.md](./shared-source-double-process.md) — Sample-level discontinuity (≈ 2× the clean-sine `max |Δsample|`) 2 samples before adjacent same-track region seams. Mechanism closed: three stacked effects — `bpn` truncation forcing `seam−1` to zero, offline harness geometry artefact (both seam positions land at the same in-block offset), and off-boundary live geometry producing a 20 ms destructive crossfade at −9.7 dB. **Fixed in SDK 0.0.159 on the WASM engine** (openDAW#311 closed; all four cells scan at ratio 1.00 with `?engine=wasm`); TS engine still measures 1.87× at 0.0.159. **Update 2026-07-16 (historical):** the repro page no longer has a `?engine=wasm` param — the app boots the WASM engine unconditionally, so the TS-path 1.87× residual above is no longer reachable from the page; the measurement is kept for the record. Repro: [`shared-source-double-process-debug-demo.html`](../shared-source-double-process-debug-demo.html).
- [voice-fadein-clip-fadein-product.md](./voice-fadein-clip-fadein-product.md) — Audible amplitude dip on the new voice's fade-in side of a crossfade between regions with different `sourceUuid`s. Mechanism confirmed: `PitchVoice` multiplied its 20 ms voice-fade-in with the clip's gain buffer, turning a linear clip fade-in into a quadratic ramp (−1.20 dB at τ −10 ms). **Fixed in SDK 0.0.159 on both engines** (openDAW#312 closed; `PitchVoice` now combines the fades by `Math.min` — OPENDAW scans at −0.05 dB vs the −0.00 dB ALIGNED target). Repro: [`voice-fadein-clip-fadein-product-debug-demo.html`](../voice-fadein-clip-fadein-product-debug-demo.html) (live audition + offline scan; configuration uses two Tape tracks to avoid the deletion described in `project-copy-deletes-overlapping-regions.md`).

- [project-copy-deletes-overlapping-regions.md](./project-copy-deletes-overlapping-regions.md) — `project.copy()` silently deletes both regions when two `AudioRegionBox`es on the same track have overlapping timeline ranges. The live engine plays the overlap fine; the copy validator removes the regions and the offline-rendered buffer is all zeros (`queryLoadingComplete` returns true on iteration 0 because there's nothing to load). The deletion also fires from a more subtle path — `AudioRegionBox.position` is `Int32Field` (truncates on assignment) while `duration` is `Float32Field`, so a fractional PPQN value assigned to both creates a sub-PPQN overlap with no overlap intended by the consumer. Workaround we used: place each region on its own track; pick seam-in-seconds values whose PPQN is integer. Repro: voice-fade CROSSFADE configuration in [`voice-fadein-clip-fadein-product-debug-demo.html`](../voice-fadein-clip-fadein-product-debug-demo.html); contrast with the separate-track configuration in [`pure-webaudio-target-debug-demo.html`](../pure-webaudio-target-debug-demo.html) which renders normally.

- [seconds-overlap-validation-unit-mismatch.md](./seconds-overlap-validation-unit-mismatch.md) — `ProjectValidation.validate()` compares `right.position < left.position + left.duration` on raw box values; Seconds-timeBase regions store `duration` in seconds while `position` is PPQN, so the comparison mixes units and realistic Seconds overlaps survive `project.copy()` undetected. Both live probe paths (`Project.invalid()`, `RegionClipResolver.validateTrack`) skip Seconds tracks entirely. Musical overlaps are detected and deleted; Seconds overlaps are not. Pin: studio-core 0.0.152 / studio-adapters 0.0.116.

- [wasm-ensure-ready-second-context.md](./wasm-ensure-ready-second-context.md) — `WasmEngine.ensureReady(context)` registers the wasm processor module only on the FIRST context it is ever called with; for any later `BaseAudioContext` it returns `true` without registering, and booting the WASM `EngineWorklet` there throws `InvalidStateError: 'engine-wasm-processor' is not defined in AudioWorkletGlobalScope`. (The deprecated `AudioOfflineRenderer.start` was the public-API route into the bug until SDK 0.0.161 deleted it with the TS engine.) `OfflineEngineRenderer` (dedicated worker) is immune. Filed upstream as [openDAW#315](https://github.com/andremichelle/openDAW/issues/315) — **closed wontfix 2026-07-16**: use `OfflineEngineRenderer` for offline renders; "The Typescript audio-engine will be removed soon." Repro: [`wasm-ensure-ready-second-context-debug-demo.html`](../wasm-ensure-ready-second-context-debug-demo.html).

- [recording-finalize-no-terminal-state.md](./recording-finalize-no-terminal-state.md) — A recording's `SampleLoader` (the `RecordingWorklet`) only ever reaches `{type: "loaded"}`; a finalization that never completes leaves it in `{type: "record"}` with no `{type: "error"}` and no terminal event, so consumers can't tell a slow finalization from a failed one (a timeout is the only net). `#finalize()` is gated on `numberOfFrames >= limitSamples` and its rejections are swallowed by `.catch(console.warn)`. The debug page measures the gate margin directly — 26/26 valid cycles finalized with a thin ~32–44 ms surplus (`deficit` −1407…−1920 frames). The rare wild symptom (stuck loader, seen 2×) did not reproduce on demand this session; the page is retained as the capture instrument (`window.__finalizeDebug`). Pin: SDK 0.0.154 / studio-core 0.0.152. Repro: [`recording-finalize-debug-demo.html`](../recording-finalize-debug-demo.html).

- [automation-simplifier-flattening.md](./automation-simplifier-flattening.md) — A slow, smooth recorded automation gesture comes back from finalize as a straight line. `RecordAutomation.simplifyRecordedEvents` is a single-pass greedy collinearity filter (not Ramer–Douglas–Peucker): it only ever tests the point *adjacent to the chord's far end*, where an arc's error against its chord vanishes by construction, so the chord keeps growing and the real deviation is unbounded by ε. Measured on a two-bar parabolic arc: 116 events → 4 (3 % retained), max deviation **0.198 unitValue = 19.8× the ε = 0.01** the pass advertises; a fast zig-zag control retains 81 % of its points but still lands 15× ε out. A second, by-design mechanism is separated in the same run: with the loop on, latch opens a new take at each wrap that grows with the playhead and front-trims the previous pass's region (`RegionClipResolver.#trimStart`), so end-to-end deviation at the original write positions reaches 0.79. Pin: SDK 0.0.170 / studio-core 0.2.4. Repro: [`automation-simplifier-debug-demo.html`](../automation-simplifier-debug-demo.html).
- [countin-metronome-boundary-click.md](./countin-metronome-boundary-click.md) — With the metronome preference DISABLED and a count-in enabled, recording plays one extra click exactly at the punch-in downbeat (1-2-3-4-**1**). WASM-engine regression vs the TS engine: the count-in→recording flip is quantum-granular against the block START, so the boundary block keeps the forced-on metronome and `Metronome::process` schedules the downbeat at `recording_start ∈ [p0, p1)`. Filed as [openDAW#367](https://github.com/andremichelle/openDAW/issues/367); no app-side workaround (forced-on ignores the preference). Pin: SDK 0.0.170, also present on upstream main. Repro: opendaw.studio (metronome off, count-in, record) or [`swipe-comping-demo.html`](../swipe-comping-demo.html) Click mode "Count-in only".

- [sample-rate-alignment-audit.md](./sample-rate-alignment-audit.md) — Systematic cross-rate/cross-BPM sample-rate alignment audit; 26 suspect sites from static sweep (Cn classification) plus 2 harness-artifact detectors registered during matrix phase = 28 total, grouped by engine area (engine-lib, transport, metronome-signature, region-player, recording-glue), plus the known #367 exemplar. **Complete:** 180/180 offline matrix cells pass (9 families x 5 bpms x 4 rates, after fixing two harness-artifact detector issues found and resolved mid-campaign) and the live multi-take recording path measured clean; register tally 3 cleared, 1 confirmed (nominal case), 2 harness-artifact (fixed), 22 open (not exercised) — zero new confirmed engine bugs, so no new upstream issues were filed. #367 (the known exemplar) reconfirmed live at 44.1 kHz. Now the standing cross-rate regression sweep to re-run after SDK upgrades. Pin: SDK 0.0.170. Harness: [`samplerate-audit-debug-demo.html`](../samplerate-audit-debug-demo.html) (unlisted).
- [recording-start-alignment-audit.md](./recording-start-alignment-audit.md) — Recording start-alignment audit: where a recorded audio take lands on the timeline, measured against a synthetic same-context digital loopback (no device latency) over 5 scenarios × 2 bpms × 2 rates × 3 repeats, plus two simultaneous-capture cells. Findings on 0.0.170: every take placed early (per-cell means −34.97…−52.51 ms on the absolute beat grid, count-in included), a loop-recording finalization hang (10 of 12 fresh repeats), a content-address collision on simultaneous byte-identical takes, and render-quantum-granular inter-track skew; two harness defects found and fixed mid-campaign (a beat-grid fencepost, a jank provocation that measured itself). Task 9 reworks the upstream fix in the SDK's own idiom (a one-shot `recordingStarted` engine report + the processor's first-frame time), root-causes the hang (a zero-duration take deleted at stop skipped the finalize call) and a head-drop in `RecordingWorklet.#finalize`, and re-measures the branch. PR and issue drafts under `drafts/`. The register's last section extends the campaign to **input-latency calibration**: a loopback routine added to the SDK on the same upstream branch (final head `66021385`, stacked on #376 and #378) plus a ground-truth page that measures it against a delay it injects itself — slope 1.0000 over ten runs on the keep-alive build with the applied cell `aligned` at +1.4 ms, a per-chain-instance two-state input delay that a stored calibration cannot follow (11 of 49 chains low at 48 kHz), one calibration call that read a whole render quantum short with verdict `ok`, and two open SDK findings (the stop path truncating input in flight; `terminate()` never tearing the audio chain down). Calibration PR prepared, not posted. Pin: SDK 0.0.170. Harness: [`recording-alignment-audit-debug-demo.html`](../recording-alignment-audit-debug-demo.html) (unlisted); standing sweep after SDK upgrades; calibration ground truth: [`input-latency-calibration-debug-demo.html`](../input-latency-calibration-debug-demo.html) (unlisted, needs the branch SDK).
